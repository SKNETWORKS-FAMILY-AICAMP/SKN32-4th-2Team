## 1. 서론 (Introduction)

### 1.1 목적

본 문서는 Smart HR RAG 챗봇을 **프로젝트 전체 단위**로 검증하기 위한 테스트
계획과 실행 결과를 소프트웨어 공학 관점에서 정리한다. 팀은 배포·Django 변환·LLM·
RAG를 별도 Git 브랜치로 병렬 개발했으므로, 형상관리 이력을 분석해 **작업 구조에
테스트 레벨을 정렬**하고, 계획→설계→실행→결함관리→종료평가의 표준 순서를 따른다.

### 1.2 범위 (Scope)

- **In-scope:** 단위·통합 테스트(현행 서비스 모듈 자동화), 서비스 간 인터페이스/연결 통합
  테스트(Django·LLM·RAG), 데이터 이관(Migration) 테스트(레거시→신규 DB),
  시스템 성능·품질 테스트, 인수/스모크 성격의 배포 파이프라인 검증, 요구사항
  추적(RTM), 결함·메트릭 관리
- **Out-of-scope:** AWS 실환경 성능 벤치(p50/p95·동시성·부하), 답변 사실성의
  통계적 자동 채점, 라이브 MySQL 연결이 필요한 반복 스모크, Qwen 모델 추론과
  `LLM/qwen-sft` 학습·평가 파이프라인

### 1.3 참조 표준 및 방법론

| 방법론 | 본 문서 적용 지점 |
|---|---|
| IEEE 829 | §3 테스트 계획 항목 구성, §4 케이스 명세, §6 실행 보고 |
| V-Model 테스트 레벨 | 단위 → 컴포넌트통합 → 인터페이스/연결통합 → 시스템 → 인수 (§3.3) |
| 테스트 설계 기법 | 동등분할·경계값·결정표·상태전이·오류추정·위험기반 (§3.4, §4) |
| 위험 기반 테스트 | HR 안내 위험도 기준 치명/주요/경미/통과 등급 (§3.6, §6.3) |

### 1.4 용어

- **테스트 레벨:** 검증 대상의 추상화 계층(단위/통합/시스템/인수).
- **심각도(Severity):** 결함이 시스템에 미치는 기술적 영향도.

## 2. 시스템 개요 및 형상 분석

### 2.1 아키텍처

3계층 RAG 챗봇이다. 사용자·채팅은 MySQL, 문서별 검색 인덱스는 각 PC의 FAISS에
저장한다.

```text
Django WEB (8000) → LLM FastAPI (8002) → RAG FastAPI (8001)
       │                                      ├─ MySQL: 사용자·채팅·document 메타데이터
       │                                      ├─ RAG/res/pdf: PDF 코퍼스(93건)
       └──────────────────────────────────────└─ RAG/vector_store: PC별 FAISS 인덱스
```

| 서비스 | 역할 | 주소 |
|---|---|---|
| `web/` | Django 5.2 웹 화면, 인증, 채팅·관리자 기능 | `127.0.0.1:8000` |
| `LLM/` | 답변 생성, 주제 분류, 근거 검증, RAG 호출 | `127.0.0.1:8002` |
| `RAG/` | PDF 등록·색인·검색·재정렬 | `127.0.0.1:8001` |

핵심 구성값: 임베딩 `jhgan/ko-sroberta-multitask`, 리랭커 `BAAI/bge-reranker-v2-m3`,
FAISS `IndexFlatL2`(768차원), 검색 후보 20·top-k 5, 답변 LLM `gpt-4o-mini`,
timeout LLM 15초 / RAG 45초 / Django 70초.

### 2.2 형상관리(Git) 분석 — 병렬 개발과 통합

모든 브랜치는 공통 조상(`162a22b` FastAPI→Django 마이그레이션)에서 갈라져 각
영역을 병렬 개발한 뒤 `main`으로 통합했다. 이 형상 구조가 **테스트 레벨 분할의
기준**이 된다.

| 브랜치 | 담당 영역 | 담당자(Git author) | 주요 커밋 | 대응 테스트 레벨 |
|---|---|---|---|---|
| `django-test1` | FastAPI→Django 변환(웹 컴포넌트) | **sanghee2411** | `162a22b` | 컴포넌트 단위·통합 |
| `deployment-test` | 배포 자동화 | **4nchez** | ECR build/push, OIDC, SSM 배포 | 인수/스모크 |
| `llm-runtime` `rag-runtime` | LLM·RAG 런타임 개발 + 세 서비스 연결 통합 | **Choi-Sangwook** | `1c47f99`, `0d06318`, `ab6ef9c`, `3d98cab`, `3667250`, `ea9196a`, `bfae3f3` | 단위·인터페이스/연결 통합·시스템 |
| `main` | 레거시 이관 + RAG·LLM 품질 안전장치 | Choi-Sangwook | `a36586b`, `1b576e8` | 전 레벨 회귀 |

> **작업 방식 (역할 분리).** Django 웹 애플리케이션은 **Django 담당자(sanghee2411)**
> 가 FastAPI에서 이관해 만들고 자체 테스트했다(`162a22b`). 배포 파이프라인은 **배포
> 담당자(4nchez)** 가 별도 트랙으로 구축했다. 이후 **LLM,RAG고도화 담당자(Choi-Sangwook)**
> 가 Django 담당자가 만든 웹에 LLM·RAG 서비스를 붙여 **세 서비스가 실제로 연결되어
> 동작하는지 직접 통합 연결 테스트**를 수행했다.

### 3.4 테스트 설계 기법 (Test Design Techniques)

블랙박스·경험 기반 기법을 대상 특성에 맞춰 적용했다.

| 기법 | 적용 예 | 해당 테스트 |
|---|---|---|
| 동등 분할 | 장치 선택 {auto·cpu·cuda·invalid}, 사용자 {관리자·일반·본인} | `test_runtime_defaults`, `users/tests` |
| 경계값 분석 | 페이지 0/1-based, 후보 상한 20, 타임아웃 15초, 청크 400/오버랩 80 | `test_rag_client`, `test_retrieval_candidate_pool` |
| 결정 테이블 | 고위험 질문×조건 → 확인유도/통과, `is_admin/is_disabled` 생략 시 보존 | `test_answer_policy`, `users/tests` |
| 상태 전이 | 채팅방 active → soft-deleted → 목록 제외 | `chat/tests` |

### 3.5 진입/종료 기준 (Entry / Exit Criteria)

- **진입:** 각 서비스 `.venv` 구성 완료, 마이그레이션 적용 가능, 테스트 DB 격리 가능.

| 레벨 | 합격 기준 |
|---|---|

| 시스템(성능) | E2E p95 ≤ 5초(스토리보드 목표), 오류 0 |
| 시스템(품질) | 위험도 등급제 — *치명* 0 목표, 잔여 치명은 사용 제한 명시 |
