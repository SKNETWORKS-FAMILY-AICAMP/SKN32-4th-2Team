## 1. 서론 (Introduction)

### 1.1 목적

본 문서는 Smart HR RAG 챗봇을 **프로젝트 전체 단위**로 검증하기 위한 테스트
계획과 실행 결과를 소프트웨어 공학 관점에서 정리한다. 팀은 배포·Django 변환·LLM·
RAG를 별도 Git 브랜치로 병렬 개발했으므로, 형상관리 이력을 분석해 **작업 구조에
테스트 레벨을 정렬**하고, 계획→설계→실행→결함관리→종료평가의 표준 순서를 따른다.

### 1.2 범위 (Scope)

- **In-scope:** 단위·통합 테스트(현행 서비스 모듈 자동화), 서비스 간 인터페이스/연결 통합
  테스트(Django·LLM·RAG), 데이터 이관(Migration) 테스트(레거시→신규 DB),
  시스템 성능·품질 테스트, 인수 성격의 컨테이너 배포 파이프라인 검증(docker compose·
  Nginx·OIDC/SSM/Parameter Store), 요구사항 추적(RTM), 결함·메트릭 관리
- **Out-of-scope:** AWS 실환경 성능 벤치(p50/p95·동시성·부하), 답변 사실성의
  통계적 자동 채점, 라이브 MySQL 연결이 필요한 반복 스모크, Qwen 모델 추론과
  `LLM/qwen-sft` 학습·평가 파이프라인

### 1.3 참조 표준 및 방법론

| 방법론 | 본 문서 적용 지점 |

## 2. 시스템 개요 및 형상 분석

### 2.1 아키텍처

3계층 RAG 챗봇이다. 사용자·채팅은 MySQL, 문서별 검색 인덱스는 각 PC의 FAISS에
저장한다.

```text
Django WEB (8000) → LLM FastAPI (8002) → RAG FastAPI (8001)
       │                                      ├─ MySQL: 사용자·채팅·document 메타데이터
       │                                      ├─ RAG/res/pdf: PDF 코퍼스(93건)
       └──────────────────────────────────────└─ RAG/vector_store: PC별 FAISS 인덱스
```

| 서비스 | 역할 | 주소 |
|---|---|---|
| `web/` | Django 5.2 웹 화면, 인증, 채팅·관리자 기능 | `127.0.0.1:8000` |
| `LLM/` | 답변 생성, 주제 분류, 근거 검증, RAG 호출 | `127.0.0.1:8002` |
| `RAG/` | PDF 등록·색인·검색·재정렬 | `127.0.0.1:8001` |

핵심 구성값: 임베딩 `jhgan/ko-sroberta-multitask`, 리랭커 `BAAI/bge-reranker-v2-m3`,
FAISS `IndexFlatL2`(768차원), 검색 후보 20·top-k 5, 답변 LLM `gpt-4o-mini`,
timeout LLM 15초 / RAG 45초 / Django 70초.

**운영 배포 형상(컨테이너, 2026-08-27 완성).** 위 3서비스는 각각 독립 컨테이너로
빌드되고 `docker compose`로 오케스트레이션된다. 외부에는 **Nginx(:80)** 만 노출되며
경로에 따라 각 서비스로 프록시한다.

```text
사용자(브라우저) → Nginx(:80)
        ├─ /        → web:8000  (Django, gunicorn 3 workers)
        ├─ /rag/    → rag:8001  (RAG FastAPI)
        ├─ /llm/    → llm:8002  (LLM FastAPI)
        └─ /static/ → static_volume (collectstatic 산출물)
   기동 순서(healthcheck 의존): web → rag → llm → nginx
   볼륨: static_volume, rag_vector_store(FAISS 부트스트랩 캐시)
```
