# 데이터 수집 및 전처리 보고서

> SMART 2팀 · 교내 LLM + RAG 문서 기반 질의응답 시스템
> 이 문서의 모든 수치는 같은 폴더의 `vector_store/` 를 직접 읽어 집계한 **실측값**이다.

## 1. 무엇을 수집했나

사내 인사·복무 규정을 근거로 답하는 챗봇이므로, **직원이 실제로 묻는 것에 답할 수 있는 문서**가 필요했다. 두 갈래로 모았다.

| 갈래 | 출처 | 건수 | 예 |
|---|---|---:|---|
| 사내 규정 | 알리오 → 한국기술교육대학교 내규관리시스템 | 15 | 복무규정, 직원인사규정, 유연근무제 운영지침 |
| 법령 | 국가법령정보센터 (법제처) | 13 | 근로기준법, 남녀고용평등법, 기간제법 (각 법률·시행령·시행규칙) |

사내 규정은 **알리오**(공공기관 경영정보 공개시스템)에서 공공기관을 고른 뒤, 해당 기관인
한국기술교육대학교의 **내규관리시스템**에 공개된 규정을 받아 왔다.

> 법령 출처는 PDF 페이지 머리말에 `법제처 / 국가법령정보센터` 가 찍혀 있어 확인된다.

원본은 `pdf/` 에 있다. 전부 PDF 이며 총 **28건**이다.

### 왜 법령까지 넣었나

법령은 **최저 기준**이고 사내 규정이 그보다 나은 경우가 많다. 연차가 그렇다 — 근로기준법은 1년 15일이지만 학교 복무규정은 근속에 따라 최대 25일이다. 직원이 알아야 하는 것은 후자다.

그렇다고 법령을 빼면, 사내 규정이 다루지 않는 질문(출산전후휴가 기간 등)에 답할 수 없다. **사내 규정을 우선하되 법령을 근거로 덧붙이는** 구성이 필요해 둘 다 넣었다.

법령 파일명에 `(법률)` `(시행령)` `(시행규칙)` 이 붙어 있는 것은 같은 법이 세 문서로 나뉘어 있기 때문이다. 조문 번호가 서로 다르므로 합치지 않고 그대로 뒀다.

## 2. 전처리 파이프라인

구현은 `RAG/rag_pipeline.py`, 설정값은 `RAG/config.py` 에 있다.

```
PDF ──▶ 페이지 추출 ──▶ 텍스트 정규화 ──▶ 청킹 ──▶ 품질 필터 ──▶ 중복 제거
                                                                    │
                                                                    ▼
                                                     임베딩 ──▶ FAISS 인덱스 저장
```

### 2.1 페이지 추출 — `PyPDFLoader`

PDF 를 **페이지 단위**로 읽는다. 페이지 번호를 메타데이터에 남겨야 답변 하단에 "복무규정.pdf p.5" 처럼 출처를 표시할 수 있다.

### 2.2 텍스트 정규화 — `_normalize_whitespace()`

PDF 에서 뽑은 텍스트는 그대로 쓸 수 없다. 다음을 처리한다.

| 처리 | 이유 |
|---|---|
| `\xa0`(비분리 공백) → 일반 공백 | HWP 로 만든 PDF 에 많다. 검색어와 글자가 달라 매칭이 안 된다 |
| 줄바꿈 통일 (`\r\n`, `\r` → `\n`) | 파일마다 개행 방식이 다르다 |
| **문단 내 단일 줄바꿈 → 공백** | PDF 는 줄 끝마다 개행이 들어간다. 두면 한 문장이 여러 조각으로 잘린다 |
| 3줄 이상 공백 → 2줄 | 문단 경계는 남기되 여백은 줄인다 |
| `page 12` 같은 머리말·꼬리말 제거 | 모든 페이지에 반복돼 검색을 방해한다 |
| 연속 공백 압축 | 표를 텍스트로 뽑으면 공백이 수십 개씩 들어간다 |

### 2.3 청킹 — `RecursiveCharacterTextSplitter`

```python
chunk_size    = 400        # 글자
chunk_overlap = 80
separators    = ["\n제", "\n\n", "\n", " ", ""]
```

**구분자 첫 번째가 `"\n제"` 인 것이 핵심이다.** 규정 문서는 `제1조`, `제2조` 로 구성되므로 **조문 경계에서 자르는 것이 가장 자연스럽다.** 그 자리를 못 찾으면 문단 → 줄 → 공백 순으로 물러선다.

겹침 80자를 둔 이유는, 조문이 400자를 넘어 여러 청크로 쪼개질 때 **앞 청크의 끝맥락을 뒤 청크가 물려받게** 하기 위해서다.

### 2.4 품질 필터 — `_is_meaningful_chunk()`

**80자 미만 청크는 버린다.** 표지, 목차, 페이지 번호만 남은 조각이 검색 결과에 섞이면 답변 근거로 쓸 수 없는 문서가 상위에 올라온다.

기호와 공백만으로 이루어진 청크도 같이 걸러낸다.

### 2.5 중복 제거

공백을 지운 본문을 서명(signature)으로 삼아 **같은 내용이 두 번 들어가는 것을 막는다.** 개정 이력이 페이지마다 반복되는 문서에서 실제로 걸린다.

### 2.6 메타데이터

청크마다 다음을 붙인다. 답변의 출처 표시와 원문 확인에 쓴다.

| 키 | 용도 |
|---|---|
| `source_file` | 화면에 표시할 문서명 |
| `page_number` | 원문 페이지 |
| `chunk_id` | 문서 내 순번 |
| `char_count` | 청크 길이 |
| `section_heading` | 청크 첫 줄 80자 — 어느 조문인지 가늠용 |

### 2.7 임베딩과 저장

```
임베딩 모델   jhgan/ko-sroberta-multitask   (한국어 문장 임베딩)
벡터 저장소   FAISS                          문서 하나당 인덱스 하나
```

**문서별로 인덱스를 나눈 것이 특징이다.** 하나의 큰 인덱스로 합치지 않았다. 문서를 추가하거나 삭제할 때 그 문서의 폴더만 만들거나 지우면 되고, 전체를 다시 임베딩할 필요가 없다. 관리자 화면에서 문서를 올리고 지우는 기능이 여기에 기댄다.

**문서 수는 사내 규정이 더 많은데 분량은 법령이 2.4배다.** 법령은 조문이 길고 부칙·별표가 붙기 때문이다.

이 불균형이 검색에 영향을 준다. 유사도 검색은 청크 단위로 이루어지므로, 같은 주제를 둘 다 다루면 **청크가 많은 법령 쪽이 구조적으로 유리하다.** 사내 규정을 우선해야 하는 서비스인데 코퍼스는 반대로 기울어 있다.

그래서 LLM 파트에서 두 가지로 보완했다.

- 답변 프롬프트에 **문서 우선순위**를 명시했다. 같은 주제를 둘 다 다루면 사내 규정을 앞세우고 법령은 근거로 덧붙인다.
- 평가용 검색기(`LLM/bench/corpus.py`)는 상위 K 의 절반을 사내 문서에 예약한다.

## 4. 검색 시점의 처리

전처리와 짝을 이루므로 함께 기록한다. 구현은 `search_across_vector_stores()`.

```
질문
 │
 ├─▶ 문서별 FAISS 인덱스에서 각 3건씩 유사도 검색
 │        └─ 거리순 상위 20건으로 후보 좁힘
 │
 ├─▶ BM25 키워드 점수 계산 (후보 20건 대상, 최댓값으로 정규화)
 ├─▶ 리랭커 점수 계산   BAAI/bge-reranker-v2-m3
 │
 └─▶ 최종 점수 = 0.7 × 리랭커 + 0.3 × BM25   →  상위 5건 반환
```

**의미 검색과 키워드 검색을 함께 쓴 이유**가 있다. 임베딩만 쓰면 "제20조" 처럼 **정확히 일치해야 하는 표현**을 놓치고, BM25 만 쓰면 "연차"와 "유급휴가" 가 같은 뜻이라는 것을 모른다. 둘을 7:3 으로 섞었다.

### 한국어 토큰 정규화

BM25 는 단어가 정확히 겹쳐야 점수가 오르는데, 한국어는 조사가 붙어 형태가 달라진다. `_normalize_korean_term()` 이 `은/는/이/가/을/를/의/에/에서/로/으로/와/과/도/만` 을 떼어낸다.

> "연차**를** 며칠" 과 "연차**는** 15일" 이 같은 `연차` 로 매칭된다.

## 5. 재현 방법

```bash
cd RAG
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
python app.py
```

서버가 뜨면 관리자 화면(`http://localhost:8001/admin_doc.html`)에서 PDF 를 올린다. 업로드 시점에 위 파이프라인이 돌고, `vector_store/<doc_id>/` 에 인덱스가 저장된다.

문서를 지우면 해당 폴더도 함께 지워진다. 그래서 `pdf/` 의 원본 개수와 `vector_store/` 의 인덱스 개수는 **운영 중 추가·삭제 이력에 따라 달라질 수 있다.**

### 주요 설정값

`RAG/config.py` 에 전부 적혀 있지만, **실제로 그 값을 읽어 쓰는 것과 코드에 직접 박혀 있는 것이 갈린다.** 값을 바꿔 다시 돌릴 때 주의해야 한다.

| 키 | 값 | `config.py` 값을 읽는가 |
|---|---|---|
| `CHUNK_SIZE` | 400 | ○ `app.py` 가 넘긴다 |
| `CHUNK_OVERLAP` | 80 | ○ `app.py` 가 넘긴다 |
| `SEARCH_TOP_K` | 5 | ○ `app.py` 가 넘긴다 |
| `SEARCH_INITIAL_CANDIDATES` | 20 | ○ `app.py` 가 넘긴다 |
| `MIN_CHUNK_LENGTH` | 80 | ✗ `_is_meaningful_chunk(min_length=80)` 에 직접 박혀 있다 |
| `EMBEDDING_MODEL` | `jhgan/ko-sroberta-multitask` | ✗ `get_embedding_model()` 에 직접 박혀 있다 |
| `RERANKER_MODEL` | `BAAI/bge-reranker-v2-m3` | ✗ `get_reranker_model()` 에 직접 박혀 있다 |

아래 셋은 `config.py` 값과 코드 값이 지금은 같아서 동작에 차이가 없다. 다만 `config.py` 만 고치면 반영되지 않는다.

임베딩은 `device="cpu"` 로 고정돼 있다(`rag_pipeline.py`). GPU 로 올리려면 그 인자를 바꿔야 한다.

## 6. 남은 개선 과제

**청크가 조문 중간에서 시작하는 경우가 있다.** 구분자 `"\n제"` 를 최우선으로 뒀지만, 한 조문이 400자를 넘으면 두 번째 청크부터는 조문 머리(`제20조(연차 유급휴가)`)가 없는 상태로 시작한다. 그러면 그 청크만 봐서는 **어느 조문인지 알 수 없다.**

실제로 "유급휴가는 1년에 얼마나" 라는 질문에서, 가산 규정(`매 2년에 1일`)은 검색됐는데 기본 일수(`15일`)가 앞 청크에 잘려 있어 답변이 불완전해진 사례를 확인했다.

**청킹할 때 각 청크 앞에 조문 머리를 붙이면** 해결된다. 조문이 페이지를 넘어 이어지는 경우가 있어 페이지 단위로만 보면 안 되고, 앞 페이지에서 이어지는 조문을 물려받아야 한다. 상세 검토는 `LLM/docs/RAG_FEEDBACK.md` 4-1 절에 정리해 두었다.
