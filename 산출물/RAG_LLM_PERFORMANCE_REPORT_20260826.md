## 1. 요약 결론

### 1.1 검색 구성

현재 93 PDF·3,681 청크에서는 **문서별 캐시 FAISS + 후보 20 + top-k 5**를
기본값으로 유지한다.

- FAISS 후보 20의 직접 검색 p50은 CPU FP32 **5,222.854ms**, CUDA FP16
  **177.524ms**였다. 실제 배포 모드 기준 CUDA가 29.42배 빨랐다.
- tuned Qdrant는 같은 후보·장치에서 FAISS와 35/35 문항의 최종 top-5 순서가
  같았지만, CUDA 후보 20 전체 p50은 **191.860ms**로 FAISS보다 느렸다.
- 후보 10은 약 45~50% 빨랐지만 후보 20과 완전히 같은 순위가 7/35뿐이고,
  top-5 원소 겹침은 80%였다. 답변 품질 검증 없이 기본값을 바꿀 근거가 부족하다.
- 런타임은 `RAG_DEVICE=auto`로 두어 GPU가 있으면 CUDA, 없으면 CPU를 사용한다.

### 1.2 안전장치 적용 전 현재 PC의 실제 답변 지연

FAISS 후보 20, CUDA, `gpt-4o-mini`로 35문항을 한 번씩 실행한 결과:

- 35/35 성공, 오류 0, `rag_degraded` 0
- p50 **2.382초**, p95 **3.602초**, 최대 **4.809초**
- 5초 초과 0건, 15초 LLM timeout 0건

따라서 과거의 “GPU에서 5초 내 응답” 목표는 이번 로컬 warm 실행에서는
충족했다. 이 수치는 현재 PC 결과이며 AWS CPU 인스턴스의 성능을 의미하지 않는다.

### 1.3 안전장치 적용 전 답변 품질

자동 지표는 주제 33/35, 파일명 기반 source hit 29/33, 자동 오인용 0건이었다.
그러나 각 답변을 실제로 제공된 context와 대조한 엄격한 수기 검수에서는 다음과
같았다.

| 등급 | 실제 RAG | 기대 문서 제한 검색 |
|---|---:|---:|
| 치명 | 9 | 2 |
| 주요 | 17 | 19 |
| 경미 | 5 | 6 |

이 표는 통계적 정확도가 아니라 **HR 안내 위험도에 따른 정성 판정 분포**다.
실제 RAG의 치명 오류는 잘못된 직군 규정 적용, 근거 없는 급여 수치, 잘못된 징계

## 2. 프로젝트 범위와 판정 기준

이번 프로젝트에서 RAG 성능은 현재 개발 PC에서 비교한다. AWS는 “서비스를
배포하고 접속·질문할 수 있는가”를 확인하는 smoke test 범위이며, AWS p50/p95,
동시성, CPU credit, 장시간 부하는 이번 보고서에서 측정하지 않는다.

검색 평가는 기대 PDF가 top-k에 포함됐는지로 계산한다. 답변 평가는 다음 기준으로
context와 수동 대조했다.

- 치명: 잘못된 금액·기간·징계·직군 규정을 단정하여 실제 행동에 영향을 줄 수 있음
- 주요: 핵심 조건·예외·절차 누락, 잘못된 거절, 문서명·조문 오귀속
- 경미: 핵심 답은 유효하나 제한적 누락 또는 표시·문장 품질 문제
- 통과: 질문에 직접 답하고 제공된 근거와 적용 범위가 일치

수기 검수는 결과 JSONL에 저장된 context와 source만 사용했다. 외부 법률 지식으로
정답을 보정하지 않았다.

## 4. 과거 26 PDF 실험

과거 `rag_test`는 26 PDF·1,414 청크, CUDA 환경에서 12질의를 워밍업한 뒤
질의마다 3회 측정했다.

| 버전 | 커밋 | min | p50 | max | mean |
|---|---:|---:|---:|---:|---:|
| baseline: 스토어마다 질문 재임베딩 | `c0fb7f7` | 725.7ms | 935.8ms | 1,378.3ms | 969.4ms |
| opt1: 질문 임베딩 1회 | `f9d2a0a` | 363.7ms | 407.6ms | 1,088.9ms | 514.5ms |
| Qdrant naive embedded exact | `bfa6204` | 307.8ms | 359.2ms | 401.2ms | 360.8ms |
| Qdrant tuned embedded exact | `117fbb7` | 324.5ms | 360.6ms | 1,027.9ms | 461.9ms |

원본 retrieval JSON 재계산에서 opt1과 Qdrant tuned는 baseline의 top-5 순서를
60/60 유지했다. naive Qdrant는 한 문서의 여러 청크가 전역 후보를 점유해 정확
top-1 청크가 8/12로 달라졌다. 이 결과로 문서당 후보 상한의 필요성을 확인했다.

과거 답변 품질표는 완전한 raw 답변 파일이 남아 있지 않고 일부 수기값과 자동값이
충돌한다. 따라서 이력으로만 보존하며 현재 결론의 근거로 사용하지 않는다.

## 5. 현재 93 PDF 검색 통제행렬

조건마다 새 프로세스, 워밍업 1회, 35문항×3회로 실행했다. HTTP와 LLM은 제외한
직접 검색 파이프라인 수치다.

| 백엔드 | 실행 모드 | 후보 | p50 | p95 | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| FAISS cached | CPU FP32 | 10 | 2,617.286ms | 2,943.974ms | 16/32 | 27/32 | 30/32 | 0.674479 |
| FAISS cached | CPU FP32 | 20 | 5,222.854ms | 5,840.997ms | 17/32 | 26/32 | 29/32 | 0.683333 |
| FAISS cached | CUDA FP16 | 10 | 97.318ms | 110.417ms | 16/32 | 27/32 | 30/32 | 0.674479 |
| FAISS cached | CUDA FP16 | 20 | 177.524ms | 209.245ms | 17/32 | 26/32 | 29/32 | 0.683333 |
| Qdrant tuned exact | CPU FP32 | 10 | 2,705.826ms | 2,998.251ms | 16/32 | 27/32 | 30/32 | 0.674479 |
| Qdrant tuned exact | CPU FP32 | 20 | 5,217.141ms | 5,872.236ms | 17/32 | 26/32 | 29/32 | 0.683333 |
| Qdrant tuned exact | CUDA FP16 | 10 | 105.421ms | 117.312ms | 16/32 | 27/32 | 30/32 | 0.674479 |
| Qdrant tuned exact | CUDA FP16 | 20 | 191.860ms | 229.762ms | 17/32 | 26/32 | 29/32 | 0.683333 |

CPU에서는 리랭커가 후보 20 기준 p50 약 5.2초로 병목을 지배했다. CUDA에서는
리랭커가 약 161~163ms로 줄었다. FAISS와 Qdrant 벡터 검색 자체는 모두 CPU이며,
CUDA 표기는 임베딩과 CrossEncoder를 CUDA로 실행했다는 뜻이다.

Qdrant는 독립 서버/HNSW가 아니라 embedded in-memory exact 비교다. 현 규모에서
최종 순위는 FAISS와 같았고 지연 이점은 없었다. 운영형 Qdrant의 필터·영속성·분산
가치까지 부정하는 결과는 아니다.

## 6. 현재 93 PDF 실제 RAG + LLM

### 6.1 자동 측정

| 조건 | 성공 | 주제 | source hit | p50 | p95 | 최대 | 5초 초과 | 15초 초과 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 안전장치 전 실제 93 PDF RAG | 35/35 | 33/35 | 29/33 | 2.382s | 3.602s | 4.809s | 0 | 0 |
| 안전장치 전 기대 문서 제한 검색 | 35/35 | 34/35 | 33/33 | 1.994s | 3.329s | 4.909s | 0 | 0 |
| 안전장치 후 수동 평가 run(15:25) | 35/35 | 33/35 | 미산정 | 2.293s | 5.960s | 6.671s | 2 | 0 |
| 안전장치 후 runtime-only run(15:55) | 35/35 | 33/35 | 미산정 | 2.235s | 5.795s | 6.353s | 2 | 0 |

안전장치 전 `source hit`의 분모 33에는 개인 잔여연차 문항이 포함되어 검색 보고서의
범위 안 32문항과 다르다. 또한 파일명만 맞으면 성공이므로 정답 조항이나 직군이
틀려도 통과할 수 있다. 안전장치 후 E2E는 검증 실패 시 사용자에게 노출할 출처를
비우므로 이 값으로 순수 검색 source hit을 다시 계산하지 않았다. 현재 검색 품질은
별도 RAG 105회 실행의 hit@5 **29/32**를 사용한다.

실제 RAG의 자동 source miss는 다음 네 건이다.

| 문항 | 판정 |
|---|---|
| `work-duty-general` | 복무규정 원문을 찾지 못한 실제 검색 실패 |
| `pay-overtime-a` | 실제 핵심 지침을 찾았지만 기대 목록이 빠진 라벨 오류 |
| `pay-holiday-work` | 근로기준법을 찾지 못한 실제 검색 실패 |
| `hire-contract-b` | 일반 기간제 대신 기간제교원 문서를 찾은 대상 혼동 |

### 6.2 안전장치 적용 전 실제 RAG의 치명 사례

| 문항 | 문제 |
|---|---|
| `leave-parental-a` | 법률·강사·임시교원 규정을 섞고 적용 대상과 기간 근거를 잘못 귀속 |
| `leave-parental-b` | 기술연구원 3년 규정을 사용자 직군 확인 없이 일반화 |
| `work-flexible-a` | 재택근무 전용 절차를 모든 유연근무 신청 절차로 일반화 |
| `work-hours` | context에 주 40시간 근거가 있는데도 찾을 수 없다고 거절 |
| `pay-severance` | context에 없는 퇴직 전 3개월과 `근로기준법 제47조`를 단정 |
| `pay-holiday-work` | 정답 문서를 못 찾은 뒤 context에 없는 150%를 단정 |
| `hire-contract-b` | 일반 기간제 질문에 기간제교원 1년·3년 규칙을 적용 |
| `disc-dui-a` | 가능한 징계 범위를 단일 처분으로 축약하고 시행일 제1조를 근거로 오인 |
| `disc-dui-b` | 징계 범위의 중간 처분을 누락하고 시행일 제1조를 근거로 오인 |

### 6.3 기대 문서 제한 검색의 의미

기대 문서 안에서만 검색하면 실제 RAG의 치명 9건이 2건으로 줄었다. 특히
`pay-severance`, `pay-holiday-work`, `hire-contract-b`, 음주운전 문항의 위험한
핵심 내용이 완화됐다. 따라서 retrieval 개선 효과는 분명하다.

그러나 이 조건도 정답 페이지·조항을 보장하지 않는다. 육아휴직과 육아기 근로시간
단축을 혼동하거나 다른 문서의 같은 조문 번호를 붙이는 오류가 남았다. 현재의
“기대 문서 검색”은 진짜 정답 oracle이 아니라 LLM 상한선에 가까운 참고 조건이다.

### 6.4 자동 인용 검사의 한계

실제 RAG 35문항의 자동 `bad_citations`는 0건이었지만 수기 검수에서는 다음과 같은
오귀속이 확인됐다.

- 시행령 제11조를 법률 제11조로 표기
- 시간외근무지침 제4조 내용을 수당규칙 제8조로 귀속
- 교내 보수규정 제47조를 근로기준법 제47조로 귀속
- 기간제 제한 제7조 내용을 제6조로 인용
- 시행규칙 제23조를 본 규정 제23조로 표기

현재 검사는 답변의 `제N조` 문자열이 합쳐진 전체 context 어딘가에 있는지만 본다.
동일 번호가 다른 문서에 있으면 잘못된 인용도 통과한다. 답변 품질을 판단할 때
자동 오인용 0건을 그대로 신뢰하면 안 된다.

## 7. 라벨과 평가 도구에서 확인된 문제

- `pay-overtime-a`: `시간외근무수당지급지침.pdf`, `수당등에관한규칙.pdf` 누락
- `leave-parental-with-maternity`: 18개월·30일 규정이 있는 시행령 누락
- `work-overseas-trip`: 직접 근거인 `공무국외출장 운영지침.pdf` 누락
- `hire-contract-b`: 기간제 직원과 기간제교원을 구분하지 않는 질문
- 직군이 다른 여러 규정이 함께 검색돼도 현재 라벨은 적용 대상을 판정하지 못함
- 일부 source 페이지가 `p.0`으로 표시되어 사용자가 실제 페이지를 확인하기 어려움

다음 평가부터는 파일명뿐 아니라 `expected_article`, `expected_facts`,
`applicable_persona`, `forbidden_claims`, `expected_action`을 함께 기록해야 한다.

## 8. 배포 설정과 timeout 해석

현재 설정은 다음 역할로 분리돼 있다.

- LLM provider timeout: 15초
- LLM → RAG 검색 timeout: 45초
- Django → LLM 전체 대기: 70초

과거 5초는 GPU FastAPI 데모의 성능 목표였고, 모든 장비에 적용하는 실패 제한이
아니다. 안전장치 적용 전에는 로컬 warm 35문항이 모두 5초 안에 끝났지만, 현재
수동 평가 run과 runtime-only 반복은 각각 2건이 5초를 넘었고 p95도 5.960초와
5.795초였다. 따라서 현재 코드는 5초 성능 목표를 충족하지 못했다. 다만 두 실행
모두 15초를 넘은 요청과 timeout 오류는 없었다. 이 로컬 수치를 AWS CPU 성능으로
해석하지 않는다.

AWS에서는 서비스 기동, health, 대표 질문 응답, 재시작 후 복구 정도만 smoke test로
확인한다. AWS 성능 벤치마크는 이번 프로젝트 목표에서 제외한다.

## 9. 최종 판단

1. 검색 기본값은 FAISS·후보 20·top-k 5를 유지한다.
2. 장치는 auto로 두어 CUDA 가능 시 GPU, 아니면 CPU로 실행한다.
3. Qdrant는 현 규모의 속도 이점이 없어 운영 요구가 생길 때 재검토한다.
4. 후보 10은 속도 옵션으로 보존하되 현재 기본값으로 승격하지 않는다.
5. 안전장치 적용 후 로컬 GPU p95는 5초 목표를 충족하지 못했지만, 15초 timeout
   초과와 API 오류는 없었다.
6. 자동 source hit과 인용 문자열 검사는 실제 답변 안전성을 보장하지 못했다.
7. 현재 버전은 AWS 배포 기술 데모에는 사용할 수 있지만 HR 규정의 최종 판단이나
   급여·징계 의사결정 도구로 소개해서는 안 된다.

## 10. 한계

- 현재 검색 통제행렬은 warm·순차 단일 요청이며 HTTP와 LLM을 제외한다.
- 수동 위험도 검수는 15:25 실행에만 적용했다. 15:55 반복은 runtime-only이며
  답변별 등급을 부여하지 않았다.
- LLM 답변 생성 반복 수가 두 번뿐이므로 변동성을 통계적으로 추정하지 않았다.
- CPU는 FP32, CUDA는 FP16이므로 29.42배는 순수 하드웨어 배율이 아니다.
- Qdrant는 embedded exact이며 실서버 HNSW 결과가 아니다.
- 35문항이 93 PDF 전체를 균형 있게 대표하지 않는다.
- 답변 수기 등급은 엄격한 정성 판정이며 통계적 정확도 점수가 아니다.
- AWS, cold start, 동시성, TTFT, GPU VRAM은 이번 범위에서 측정하지 않았다.
- 기대 문서 제한 검색도 정답 페이지·조항을 보장하지 않는다.
