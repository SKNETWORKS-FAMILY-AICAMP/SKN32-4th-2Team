# 1. 지금 적용되어 있는 것

## 1.1 서비스 구조

| | |
|---|---|

| 상태 | **stateless** — DB 연결 없음. 저장은 WEB 담당 |
| 프로바이더 | OpenAI `gpt-4o-mini`(기본) / Gemini `gemini-3.5-flash` — 요청별 전환 |

| 엔드포인트 | `/v1/chat`, `/v1/chatroom-name`, `/health` (+ 미사용 `/v1/chat/stream`, 운영용 `/v1/topic`) |

## 1.2 답변 생성

- RAG 검색 결과를 `[참고 문서]` 블록으로 조립해 질문 **앞에** 배치
- 시스템 프롬프트에 6개 규칙 (근거 기반 / 조문 인용 / 3~6문장 / 지어내기 금지 등)
- `temperature=0.2`
- **답변 생성과 주제 분류를 `asyncio.gather` 로 병렬 실행** — 순차 대비 분류 지연만큼 절약

## 1.3 주제 분류 — 3중 안전장치

도넛 차트의 `GROUP BY` 축이라 값이 흔들리면 안 됩니다.

1. **enum 제약 디코딩** — OpenAI Structured Outputs(`strict:true`), Gemini `response_schema` enum.
   목록 밖 값이 *생성 자체가 불가능*합니다. `seed` 는 쓰지 않습니다 (두 벤더 모두 best-effort 이고, 입력 문장이 조금만 달라지면 무의미)
2. **화이트리스트 검증** — 그래도 이상하면 `기타`
3. **정규화 해시 캐시** — `"연차 며칠?"` == `"  연차 며칠???  "` 동일 처리. 시연 재현성 + 호출비 절감

실제 API 검증: 두 프로바이더 모두 **enum 8종 이탈 0건**.

## 1.4 RAG 연동

- `POST /api/search` 호출 (Member C 실제 구현에 맞춘 형태)
- **절대경로 → 파일명** 변환 (`D:\study\...\복무규정.pdf` → `복무규정.pdf`) — 남의 PC 경로 노출 방지
- `page` 0-based → `page_label` 1-based 보정
- `(파일명, 페이지)` 기준 중복 제거
- `top_k` 를 RAG 가 안 받으므로 개수 제한은 이쪽에서
- **RAG 가 죽어도 500 을 안 던짐** → `200 + rag_degraded:true` 로 문서 없이 답변

## 1.5 후속 질문 대응 (준비만 완료)

`history` 가 비면 질문 독립 처리, 채워 오면 직전 질문을 검색어 앞에 붙입니다.
**WEB 이 배열을 채우는 순간 자동 전환**되며 API 계약도 이쪽 코드도 안 바뀝니다.

## 2.1 벤치마크 (`bench/`)

```
bench/
├── questions.yaml    질문 25~30개 + 정답 근거 문서 + 정답 카테고리
├── run_bench.py      OpenAI/Gemini 반복 실행 → logs/metrics.jsonl
└── report.py         집계 → 표·그래프 → docs/PERFORMANCE_REPORT.md
```

측정 항목:

| 축 | 지표 |
|---|---|
| 속도 | TTFT, 총 응답시간 (p50 / p95) |
| 비용 | prompt/completion 토큰, 요청당 원화 |
| 검색 정확도 | 정답 문서가 `sources` 에 포함된 비율 (recall@k) |
| 분류 정확도 | 정답 카테고리 일치율 + **패러프레이즈 일관성** |
| 안정성 | 타임아웃·에러율 |

`questions.yaml` 은 같은 의도를 3가지로 바꿔 쓴 세트를 포함시켜 **도넛 차트 신뢰도의 근거**로 삼습니다.

## 2.2 스트리밍 토큰 집계

지금 `/v1/chat/stream` 은 `prompt_tokens`/`completion_tokens` 가 `null` 입니다.

- OpenAI: `stream_options={"include_usage": True}`
- Gemini: 스트림 마지막 청크의 `usage_metadata`

## 2.3 429 재시도 — ✅ 완료 (범위: 측정 도구 한정)

**Gemini 무료 티어 = 분당 20회** (실측 확인). 질문 34개 × 2 프로바이더면 계속 걸립니다.

> **팀 결정: 이건 테스트 환경 문제로만 둔다.**
> 실서비스는 무료 티어를 쓰지 않고, 시연에서도 분당 20회를 연속으로 칠 일이 없습니다.
> 따라서 **서비스 코드에는 재시도를 넣지 않았습니다.** 429 를 받으면 바로
> `429 LLM_RATE_LIMITED` 로 돌려주고 판단은 호출자에게 맡깁니다
> (벤더 권장 대기가 30초 이상이라 요청 타임아웃 5초 안에 처리할 수 없기도 합니다).
>
> 재시도와 호출 간격 제어는 `bench/throttle.py` 에만 있습니다. 제가 무료 티어로
> 벤치마크를 돌려야 해서 필요한 것이고, 서비스 동작과는 무관합니다.

측정 중 확인: `/v1/chat` 한 번이 프로바이더를 **2회** 호출한다(답변 생성 + 주제 분류).
분당 20회 한도에서 실질 요청 한도는 **분당 10회**다. 34문항을 Gemini 로 돌리면 최소 3.4분.

# 3. 프롬프트 엔지니어링 — 적용 후보

> **원칙: 측정 없이 바꾸지 않는다.**
> 아래 항목은 벤치마크가 먼저 돌아간 뒤, 하나씩 켜고 끄며 수치로 비교합니다.
> 그래야 성능 보고서에 "왜 이렇게 했는지"를 근거로 쓸 수 있습니다.

## 3.1 Few-shot 예시 추가

지금은 규칙만 나열된 zero-shot 입니다. **좋은 답변 2~3개를 예시로** 넣으면 형식이 안정됩니다.

```
[예시]
질문: 연차 며칠까지 쓸 수 있나요?
답변: 근로기준법 제60조에 따라 1년간 80% 이상 출근한 근로자에게 15일이 부여됩니다.
      개인별 잔여일수는 인사팀에서 확인하실 수 있습니다.
```

비용: 프롬프트 토큰 증가. 단 시스템 프롬프트는 고정이라 **프롬프트 캐싱 대상**이 됩니다(3.6).

## 3.2 부정 지시 → 긍정 지시

`"지어내지 마세요"` 보다 `"[참고 문서]에 있는 문장만 근거로 쓰세요"` 가 잘 먹힙니다.
LLM 은 "하지 마라"보다 "이렇게 하라"에 더 안정적으로 반응합니다.

실제로 이번에 겪은 문제이기도 합니다 — 규칙 5("개인 정보는 답하지 말라")가 과하게 작동해
**근거가 있는데도 "찾을 수 없습니다"** 라고 답했습니다. 긍정 지시로 바꿔 해결했습니다.

## 3.3 문서 번호 인용 유도

`[참고 문서]` 블록에 `[문서 1] [문서 2]` 번호를 이미 붙이고 있습니다.
**답변에서 그 번호를 인용하게** 하면 어느 문서를 근거로 썼는지 추적할 수 있습니다.

```
답변: ... 15일이 부여됩니다 [문서 1].
```

→ `sources` 중 실제로 쓰인 것만 추려 화면에 표시 가능. **할루시네이션 탐지**에도 쓸 수 있습니다
(존재하지 않는 번호를 인용하면 근거 없이 답한 것).

## 3.4 temperature 낮추기

현재 답변 생성은 `0.2`. 규정 안내는 창의성이 필요 없으므로 **`0.0`** 이 나을 수 있습니다.
같은 질문에 같은 답이 나와야 시연도 안정적입니다. 분류는 이미 `0`.

## 3.5 `max_tokens` 하드 제한

"3~6문장" 은 프롬프트 지시일 뿐 강제력이 없습니다. `max_tokens` 로 상한을 두면
비용 상한이 생기고 응답 시간도 예측 가능해집니다. 다만 **문장 중간에 잘릴 위험**이 있어
여유를 두고 정해야 합니다.

## 3.6 프롬프트 캐싱 (비용)

OpenAI 는 프롬프트 앞부분이 동일하면 자동으로 캐시가 걸립니다.
**시스템 프롬프트를 맨 앞에 고정**하고 변하는 부분(참고 문서·질문)을 뒤로 몰면 캐시 적중률이 올라갑니다.
현재 구조가 이미 그렇지만, few-shot 을 넣을 때 순서를 지켜야 합니다.

## 3.7 모호한 질문 처리

`"휴가"` 처럼 한 단어만 오면 지금은 그냥 답합니다.
**되묻게 하는 규칙**을 넣을지 검토 — 다만 시연에서는 답이 바로 나오는 편이 나을 수 있어 트레이드오프입니다.

## 3.8 프롬프트 버전 관리

`app/prompts.py` 한 곳에 모여 있습니다. 버전을 상수로 붙이고 **계측 로그에 함께 기록**하면
"프롬프트 A 대비 B 가 몇 % 개선" 을 보고서에 쓸 수 있습니다.

## 3.9 주제 분류 방법 비교 — 벤치마크 항목

지금은 주제 분류에 LLM API 를 한 번 더 부른다. 실측 비용은 **1회 0.09원**
(입력 403토큰 + 출력 9토큰, gpt-4o-mini 기준), 1만 회에 922원이다.
답변 생성과 병렬로 돌아 사용자 대기 시간에는 0을 더한다.

즉 비용·지연은 논점이 아니다. 바꿀 만한 이유는 따로 있다.

- 프로바이더 호출이 요청당 2회 → 1회가 되면 레이트리밋 여유가 2배
- LLM API 가 죽으면 분류도 같이 죽는다(현재는 `기타` 폴백)
- **어느 방법이 나은지 데이터로 답할 수 있다** ← 보고서에서 제일 큰 가치

후보:

| 방법 | 장점 | 단점 |
|---|---|---|
| **LLM enum (현행)** | enum 제약으로 목록 이탈 불가, 검증 완료 | API 호출 1회 추가 |
| 답변+주제 단일 호출 | 호출 절반 | 답변이 JSON 에 갇혀 스트리밍 곤란, 품질 저하 우려 |
| 임베딩 zero-shot | API 0회, ~10ms, 완전 결정적 | 모델 500MB, 정확도 미지수 |
| 키워드 규칙 | 무료·즉시 | 표현 변화에 취약 (mock 이 "반차"를 기타로 보낸 사례) |

**측정 전에는 바꾸지 않는다.** `bench/questions.yaml` 34문항에 정답 카테고리가
이미 라벨링되어 있으므로, `run_bench.py` 에서 방법별로 나란히 돌려 정확도·일관성·
지연·비용을 비교한다. 결과에 따라 채택하거나, "왜 LLM 을 쓰는가"의 근거로 삼는다.

> 임베딩 방식은 카테고리 이름·설명을 임베딩해 비교하는 **zero-shot** 으로 한다.
> 34문항을 중심점 학습에 쓰면 같은 문항으로 평가할 때 정답을 미리 본 셈이라
> 수치가 부풀려진다.

# 4. 검색 품질 — 내 쪽에서 할 수 있는 것

RAG 서비스 코드를 건드리지 않고 개선 가능한 부분입니다.

## 4.1 `top_k` 스윕

3 / 5 / 10 을 바꿔가며 **정확도와 비용의 균형점**을 찾습니다.
많을수록 좋은 게 아닙니다 — 노이즈가 늘고 프롬프트가 비대해집니다.

## 4.2 컨텍스트 순서 재배치 (lost in the middle)

LLM 은 긴 컨텍스트의 **중간에 있는 정보를 잘 놓칩니다.**
가장 관련도 높은 문서를 **맨 앞과 맨 뒤**에 배치하면 개선되는 것으로 알려져 있습니다.
현재는 관련도 순으로 그냥 나열하고 있어, 재배치 전후를 비교해볼 만합니다.

## 4.3 청크 길이 제한

RAG 는 `chunk_size=1000` 으로 자릅니다. 5건이면 **약 5,000자**가 프롬프트에 들어갑니다.
질문과 무관한 조문까지 통째로 실리므로, 필요한 부분만 발췌하거나 상한을 두는 방안을 검토합니다.

## 4.4 검색어 재작성

현재는 "직전 사용자 질문 + 현재 질문" 을 이어붙이는 단순 방식입니다.
LLM 으로 독립 질문을 만드는 방식이 더 정확하지만 **호출이 1회 늘어** 5초 예산을 압박합니다.
`history` 를 실제로 쓰기 시작한 뒤에 판단합니다.

# 5. 안정성

## 5.1 프로바이더 폴백

OpenAI 실패(429/장애) 시 Gemini 로 자동 전환. **시연 중 사고 방지**가 목적입니다.
다만 타임아웃 예산 안에서 재시도해야 하므로, 첫 호출 타임아웃을 짧게 잡아야 합니다.

## 5.2 타임아웃 재검토
