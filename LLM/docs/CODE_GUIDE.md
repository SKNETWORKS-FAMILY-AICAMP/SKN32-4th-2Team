# LLM 서비스 코드 안내

발표와 질의응답을 위한 문서다. **어디에 무엇이 있고, 요청이 어떤 순서로 흐르며,
성능을 어떻게 올렸는지**를 정리했다.

- 설계 배경과 그때그때의 판단 → [README.md](../README.md)
- 측정 결과 → [PERFORMANCE_REPORT.md](PERFORMANCE_REPORT.md)
- WEB 이 쓰는 API 계약 → [API.md](API.md)

## 1. 폴더 구조

```
LLM/
├── app/                    ← 서비스 (운영에 실제로 도는 코드)
│   ├── main.py             FastAPI 앱. 기동/종료 훅, 로깅, CORS
│   ├── config.py           .env 로드. 모든 설정의 단일 출처
│   ├── schemas.py          요청/응답 모델 = WEB 과의 계약
│   ├── domain.py           카테고리 8종, 길이 상한, 내부 청크 모델
│   ├── errors.py           에러 코드 6종 + 한국어 메시지
│   ├── prompts.py          시스템 프롬프트. 튜닝은 여기서만 한다
│   ├── metrics.py          지연/토큰을 JSONL 로 기록
│   ├── routers/
│   │   ├── chat.py         POST /v1/chat, /v1/chat/stream
│   │   └── meta.py         POST /v1/topic, /v1/chatroom-name, GET /health
│   ├── providers/          모델 벤더를 감싸는 계층
│   │   ├── base.py         LLMProvider 인터페이스 (generate/stream/classify/preconnect)
│   │   ├── openai_provider.py
│   │   ├── gemini_provider.py
│   │   ├── qwen_provider.py    Ollama 경유 (로컬)
│   │   ├── mock_provider.py    키 없이 UI 붙여볼 때
│   │   └── registry.py     이름 → 인스턴스, 기동 시 예열
│   └── services/           실제 일을 하는 곳
│       ├── answer.py       ★ 핵심. 검색 → 생성 → 후처리
│       ├── topic.py        주제 분류 + 캐시 + 검증
│       ├── naming.py       채팅방 이름
│       └── rag_client.py   RAG 서비스 HTTP 호출
│
├── bench/                  ← 측정 도구 (운영에 안 쓰임)
│   ├── questions.yaml      평가 문항 35개 + 정답 라벨
│   ├── run_bench.py        문항을 서비스 경로로 돌려 JSONL 기록
│   ├── report.py           JSONL → PERFORMANCE_REPORT.md
│   ├── judge.py            답변이 근거에 뒷받침되는지 채점 (LLM-as-judge)
│   ├── trace_claim.py      근거 없는 문장이 코퍼스에는 있는지 추적
│   ├── variants.py         프롬프트 후보 모음 (A/B 비교용)
│   ├── corpus.py           벤치용 로컬 PDF 검색 (RAG 대역)
│   └── throttle.py         벤치용 호출 속도 제어
│
├── qwen-sft/               ← 곁가지 실험 (운영에 안 쓰임)
│                           Qwen2.5 파인튜닝 — 채택 보류. 학습·평가 스크립트와 보고서
│
├── docs/                   문서
├── scripts/                보조 도구 (.env.example 드리프트 검사)
├── local/                  로컬 실행 스크립트 (git 미포함)
├── logs/                   계측 로그 (git 미포함)
└── requirements.txt
```

**`app/` 과 `bench/` 를 나눈 것이 이 구조의 핵심이다.**
`bench/` 는 운영 코드를 전혀 건드리지 않고, `app/` 의 함수를 그대로 호출해서 잰다.
그래서 "벤치에서는 잘 나오는데 실제로는 다르다" 는 일이 생기지 않는다.

## 2. 요청 하나가 흐르는 순서

`POST /v1/chat` 에 질문이 들어왔을 때다.

```
WEB (8000)
  │  {"chatroom_id": "...", "message": "유급휴가는 1년에 얼마나 주어지나요?"}
  ▼
routers/chat.py          요청 검증 (schemas.ChatRequest)
  ▼
services/answer.py  generate_answer()          ★ 여기가 전부다
  │
  ├─1. build_search_query()   이력이 있으면 직전 질문을 앞에 붙임
  │
  ├─2. rag_client.search()  ──────────► RAG (8001) /api/search
  │      · 응답 필드 매핑 (source_file → 파일명, page_number → 페이지)
  │      · 관련도 RAG_MIN_SCORE 미만 결과 버림
  │      · (파일, 페이지) 중복 제거, top_k 개로 자름
  │      · 실패하면 예외 대신 (빈 목록, degraded=True) 반환
  │
  ├─3. asyncio.gather (동시 실행)
  │      ├─ provider.generate()   답변 생성   ─► OpenAI
  │      └─ topic.classify()      주제 분류   ─► OpenAI
  │                                  · 캐시 조회 → 없으면 enum 제약 호출
  │                                  · 화이트리스트 검증
  │
  ├─4. strip_unverifiable_citations()   근거에 없는 조문 번호 제거
  │
  ├─5. metrics.record_chat()            지연·토큰을 logs/metrics.jsonl 에
  │
  ▼
{"answer": "...", "topic": "휴가/휴직", "sources": [...], "rag_degraded": false}
  │
  ▼
WEB 이 chat / chat_source 테이블에 저장
```

LLM에는 `DATABASE_URL`이 없습니다. Django WEB과 RAG가 같은 신규 DB `rag_chatbot_v4`를
소유하며, 이전 DB가 있는 경우에도 사용자·채팅·`chat_source` 표시 스냅샷만 WEB 이관 도구로
가져옵니다. `document`·PDF·`vector_store`는 이관하지 않고 새 RAG 코퍼스에서 다시 만듭니다.

### 각 단계에서 실제로 하는 일

**1. 검색어 만들기** (`build_search_query`)
이력이 없으면 질문 그대로 보낸다. 이력이 있으면 **직전 사용자 질문을 앞에 붙인다** —
"그럼 반차는?" 같은 후속 질문이 그 문장만으로는 엉뚱한 문서를 물어오기 때문이다.
길이 상한(500자)에 걸리면 **현재 질문은 절대 자르지 않고** 앞에 붙는 이전 질문을 줄인다.

**2. 검색** (`rag_client.search`)
RAG 응답을 내부 모델로 바꾸는 어댑터다. RAG 쪽 필드명이 여러 번 바뀌어서
알려진 이름을 모두 받도록 해뒀다. `metadata.source` 는 담당자 PC 의 절대경로라
파일명만 잘라 쓴다 — 그대로 두면 사용자 화면에 남의 경로가 노출된다.

**3. 생성 + 분류 동시 실행**
둘은 서로의 결과가 필요 없다. 순서대로 하면 분류 시간이 사용자 대기에 그대로 더해진다.

**4. 후처리** (`strip_unverifiable_citations`)
답변이 든 조문 번호가 검색된 근거에 실제로 있는지 대조한다. 없으면 **번호만** 뺀다
("근로기준법 제57조에 따르면" → "근로기준법에 따르면"). 문장을 통째로 지우면
뜻이 바뀌기 때문이다. 현재 `ANSWER_CITE_ARTICLES=false` 라 조문 번호를 아예 뺀다.

**5. 계측**
지연·토큰·모델명은 API 응답에 넣지 않는다. WEB 이 저장할 이유가 없고,
성능 보고서는 이 로그를 읽어 집계한다.

## 3. 알아둘 설계 결정 5가지

질문이 들어올 만한 것들이다.

### (1) 이 서비스는 DB 에 붙지 않는다

질문을 받아 답변·주제·근거를 JSON 으로 돌려줄 뿐이고, 저장은 WEB 이 한다.
그래서 **WEB·RAG 가 완성되기 전에도 이 파트를 끝까지 만들 수 있었다.**

현재 대상 DB는 `rag_chatbot_v4`이지만, 이는 WEB/RAG 설정값이다. LLM의 `.env`에는
`DATABASE_URL`·`RAG_DB_NAME`·`LEGACY_DATABASE_URL`을 추가하지 않고 `RAG_BASE_URL`만 둔다.

### (2) 프로바이더 계층을 따로 뒀다

`services/` 는 어느 모델을 쓰는지 모른다. `providers/base.py` 의 인터페이스만 안다.
덕분에 성능 비교 때 프로바이더만 바꿔 끼우면 됐다. LangChain 같은 래퍼를 쓰지 않은
이유도 여기 있다 — 토큰·지연을 정확히 재려면 SDK 를 직접 부르는 편이 낫다.

### (3) 주제는 '생성' 이 아니라 '분류'

대시보드 도넛 차트가 `chat.topic` 을 묶어 그리는데, LLM 이 매번 다른 문구를 뱉으면
차트가 조각난다. `seed` 고정은 입력이 완전히 같을 때만 의미가 있어 답이 아니다.
**enum 제약 디코딩**으로 목록 밖 토큰을 디코더 단계에서 차단한다.
그 위에 화이트리스트 검증과 정규화 해시 캐시를 뒀다(`topic.py`).

### (4) RAG 실패는 에러가 아니다

검색이 안 되면 500 을 던지지 않고 `rag_degraded: true` 와 함께 답변을 돌려준다.
문서 없이라도 답하는 편이 사용자에게 낫다.

### (5) 관련 문서가 없으면 모른다고 답한다

RAG 는 관련 문서가 없어도 자리를 무관한 청크로 채운다. 그러면 모델이 "근거가 있다"
고 착각해 지어낸다. 리랭커 점수가 `RAG_MIN_SCORE` 미만이면 버리고,
남는 게 없으면 "규정에서 찾을 수 없습니다" 로 안내한다.

## 4. 성능을 어떻게 올렸나

**전부 측정한 값이다.** 원본은 `bench/results/*.jsonl`(git 미포함),
집계는 [PERFORMANCE_REPORT.md](PERFORMANCE_REPORT.md).

### 속도

| 개선 | 방법 | 결과 |
|---|---|---|
| 답변·주제 동시 실행 | `asyncio.gather` | 분류 지연이 대기시간에 안 더해짐 |
| 기동 시 예열 | 프로바이더 생성 + 커넥션 2개 선점 | 첫 요청 **약 3초 단축** |
| 출력 토큰 상한 | `ANSWER_MAX_TOKENS=500` | 최대 지연 **57초 → 13.9초**(Qwen) |
| Qwen 모델 상주 | `keep_alive` + 실제 로딩 예열 | 첫 응답 **7.2초 → 1.9초** |

예열은 원인을 재보고 나서야 알았다. 프로바이더 객체 생성에 1.5~2.4초,
벤더와의 TLS 연결에 0.7초가 들고 있었고, **첫 사용자가 그 비용을 대신 내고 있었다.**
Qwen 쪽은 예열 코드가 모델 *존재 확인*만 하고 실제 로딩을 안 해서 4초를 더 물었다.

### 정확도

| 개선 | 방법 | 결과 |
|---|---|---|
| 주제 분류 | 카테고리에 **경계 정의**를 문장으로 추가 | **88% → 97%** |
| 조문 인용 | 근거에 있는 번호만 인용하도록 + 코드 검증 | 오인용 **0건** |
| 근거 없는 답변 | "짚을 수 없으면 꺼내지 마라" | **19 → 15 / 35** |

주제 분류 개선이 가장 컸다. 카테고리를 **이름만** 주니 모델이 뜻을 몰라
글자 겹침으로 추측했다 — 질문에 "복무" 가 들어가면 무조건 당시 이름이던
`복무/징계` 로 갔다. 경계를 문장으로 적으니 해결됐고, **기준선을 다시 돌려 틀린
문항 ID 까지 똑같이 재현되는 것을 확인**해 우연이 아님을 보였다.

**다만 그건 증상을 덮은 것이었다.** 원인은 이름 자체다 — '비위·징계' 를 뜻하려고
지었는데 한국어에서 "복무" 는 그냥 '근무한다' 는 뜻으로도 쓰인다. 카테고리를
`징계/행동강령` 으로 바꾸고 다시 재니, "복무" 때문에 끌려오던 오답이 사라지고
**같은 97% 를 더 짧은 프롬프트로** 얻었다(나쁜 이름을 막으려고 넣었던 방어 문장
두 줄이 필요 없어졌다). 설명으로 덮기 전에 이름을 의심하는 편이 낫다.

### 신뢰도

| 개선 | 방법 | 결과 |
|---|---|---|
| 습관적 확인 안내 | 덧붙여도 되는 경우를 둘로 못박음 | **71% → 6%** |
| 범위 밖 질문 | 회사와 접점 없으면 서비스 안내로 분리 | 8/9 정확 |
| 관련도 미달 결과 | `RAG_MIN_SCORE` 로 버림 | 근거 없이 답하는 일 없음 |

"인사팀에 문의하세요" 가 답변 열에 일곱 꼴로 끝에 붙고 있었다. 사내 규정을 근거로
답해 놓고 다시 규정을 확인하라는 순환이라 **근거 있는 답변까지 못 믿게 만든다.**

세는 기준은 *답변의 마지막 문장*이 확인 안내인 경우다 — 규정 본문에 실제로 "인사팀에
신청한다" 가 들어 있는 경우까지 묶어 세면 안 되기 때문이다. 기준선 24/34,
현재 2/35. 남은 2건은 "제 연차가 며칠 남았는지" 처럼 **개인 데이터라 규정으로는
답할 수 없는 질문**이라, 이건 남아 있는 편이 맞다.

### 비용

문항당 입력 약 4,200 토큰, 출력 약 140 토큰. 10,000건에 **9,869원**.
비용의 대부분이 입력인데 참고 문서를 프롬프트에 넣기 때문이다.
→ **답변을 짧게 만드는 것보다 검색 청크 수를 줄이는 쪽이 훨씬 크게 작용한다.**
주제 분류 호출이 전체의 18% 라, 이것만 로컬 모델로 넘겨도 그만큼 준다.

### 개선 방법을 어떻게 찾았나

프롬프트를 감으로 고치지 않으려고 **측정 도구를 먼저 만들었다.**

1. `questions.yaml` — 실제 코퍼스에서 뽑은 35문항. 패러프레이즈 7묶음, 범위 밖 3개
2. `run_bench.py` — 서비스 경로 그대로 돌려 문항별 결과를 JSONL 로
3. `variants.py` — 프롬프트 후보를 한 커밋 안에 모아 A/B 비교
4. `judge.py` — 답변이 근거에 뒷받침되는지 채점
5. `trace_claim.py` — 근거 없는 문장이 코퍼스에는 있는지 추적

5번이 판을 바꿨다. "근거 없음" 으로 잡힌 23건 중 **20건(87%)이 코퍼스에는 있는데
검색이 못 찾아온 것**이었다. 모델이 지어낸 게 아니라 **검색 문제**였다는 뜻이라,
프롬프트를 더 만지는 대신 RAG 담당자에게 넘길 근거가 됐다.

## 5. 자주 나올 질문

**Q. 왜 서버를 세 개로 나눴나?**
넷이 한 코드베이스를 고치면 충돌이 난다. API 만 맞춰두면 각자 진행할 수 있고,
장애도 격리된다 — RAG 가 죽어도 챗봇은 답한다.

**Q. 97% 는 무엇의 정확도인가?**
**주제 분류** 정확도다. 답변 내용의 사실 정확성은 자동 채점하지 않았고,
근거 문서 포함 여부와 표본 수동 검수로 확인했다.

**Q. 답변이 틀리면?**
근거 문서를 항상 함께 표시해 사용자가 원문을 확인할 수 있게 했다.
근거가 없으면 지어내지 말고 "규정에서 찾을 수 없습니다" 로 답하게 했다.

**Q. 응답 속도는?**
p50 2.4초, p95 4.8초(실제 RAG 연동 기준). 기획 기준 5초에 거의 걸쳐 있다.
